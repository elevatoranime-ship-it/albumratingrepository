# Пространство · альбомы и оценки

Тёмный закрытый сайт для двоих: общая коллекция альбомов и синглов, оценки по
трекам и релизам, профили артистов и рейтинги. Матовый монохром, тёплый белый, деликатная
пыльная лаванда, плавные анимации. Полностью адаптирован под мобильные.

## Возможности

- Вход по профилю → пароль (два участника, один — админ).
- Карточки альбомов (обложка, год, тип релиза, средний балл).
- Добавление альбома: подсказки артистов, обложка файлом/ссылкой, защита от дублей.
- Страница альбома: добавление или замена обложки **после создания** (файл/ссылка,
  предпросмотр, сохранение или отмена); оценка **каждого трека** слайдером/числом
  (до 2 знаков), средний балл альбома в реальном времени.
- Подтверждение («фиксация») своей оценки на треке; итог альбома считается
  подтверждённым, только когда оба участника подтвердили все оценки.
- Фиты: в названии трека `ft.` / `feat.` / `&` открывает поле «при участии»;
  имя фитующего артиста становится ссылкой с синим неоном.
- Профиль артиста: средний балл крупно, личные альбомы и раздел «при участии».
- Синглы: переключатель **«альбомы | синглы»** на главной, отдельная страница
  сингла (одна оценка на релиз целиком), рейтинг синглов (только релизы, подтверждённые
  всеми участниками) и экран добавления сингла — с полем привязки к альбому.
- Оценка трека-сингла и самого сингла — **одна и та же**: подтвердили балл на альбоме —
  сингл получил ту же оценку и то же подтверждение (и попал в рейтинг синглов, если
  подтвердили оба участника); поставили балл на странице сингла — он виден и зафиксирован
  на его треке в альбоме и учтён в среднем альбома. Уже выставленные оценки при первом
  открытии сводятся автоматически.
- Метки синглов на треках: на странице альбома трек можно отметить как сингл —
  появляется бейдж и автоматически создаётся карточка сингла (название, год и
  обложка берутся у альбома). Привязанный сингл сам становится треком альбома,
  а сингл от другого артиста — совместкой «Название & Артист» со ссылкой на профиль.
- Рейтинг артистов: сортировка по среднему баллу, топ-3 с золотой/серебряной/
  бронзовой подсветкой, аватар — обложка лучшего альбома; синглы входят в тот же
  средний балл, учитываются только подтверждённые оценки.
- «Мой профиль»: аватар (применяется везде) и смена никнейма.
- Drag & drop треков (на десктопе), фиксация названий и количества (админ),
  целостность/тип релиза — финальный необратимый выбор, удаление альбома с
  анимацией «осыпания» обложки.
- Живая синхронизация между участниками без перезагрузки страницы: Supabase Realtime
  и резервная фоновая сверка каждые 5 секунд, пока вкладка видима.

## Совместное оценивание без перезагрузки

Изменения оценок, подтверждений и удаления подхватываются на открытой странице.
Обновляются средние баллы треков и альбома, вклад каждого участника и статус
подтверждения; главная, профиль артиста и рейтинг также показывают свежие данные.
Бейдж с баллом второго участника, как и раньше, виден **только после подтверждения**;
его неподтверждённый балл участвует в средних значениях на страницах (трека, альбома,
сингла), но **не в рейтингах** — там считаются только подтверждённые оценки.
Оценки синглов синхронизируются так же, как трековые: своя очередь записи на релиз,
защита черновика от старых ответов и подписка на изменения `single_ratings`.

- События Realtime объединяются в последовательные фоновые чтения. Событие,
  пришедшее во время запроса, ставит следующую сверку в очередь, а не теряется.
- Если WebSocket недоступен или событие пропущено, видимая вкладка сверяется с
  базой раз в **5 секунд** (плюс время сетевого запроса). При возвращении на вкладку,
  фокусе окна, восстановлении сети и подключении Realtime сверка запускается сразу.
  В скрытой вкладке и без сети фоновые чтения приостанавливаются; при выходе
  из аккаунта подписка и таймеры очищаются. Зависшее чтение отменяется через 10 секунд.
- Для обновления оценок **не пересоздаются строки треков и поля ввода**: сохраняются
  фокус, незавершённый ввод, положение слайдера и прокрутка. Изменение структуры
  треков откладывается до окончания ввода, переименования или перетаскивания.
- Свои ещё не сохранённые значения защищены от старых ответов сервера.
  Изменение балла, очистка и подтверждение идут через одну очередь записи на трек.
  Ошибка записи действительно показывается как «ошибка», а не «сохранено»;
  черновик остаётся в текущем сеансе и повторяется при возвращении сети/фокуса
  либо следующем редактировании. **При выходе из аккаунта или перезагрузке
  несохранённые черновики не сохраняются.**

Используются существующие таблицы, политики доступа и канал Supabase: новой базы
или миграции для этого изменения не требуется. Даже если публикация Realtime
не настроена, резервная сверка продолжает работать при доступном чтении базы.
В демо-режиме изменения между вкладками одного браузера подхватываются через
события localStorage; данные между разными устройствами в демо не передаются.

## Синглы

Синглы — те же релизы, что и альбомы, но с типом `single` в таблице `albums`:
отдельная оценка на релиз целиком (без треков) и необязательная привязка к альбому.
Наверху главной есть переключатель **«альбомы | синглы»**, выбор запоминается в
браузере. Кнопка справа («рейтинг артистов» / «рейтинг синглов») открывает рейтинг
текущего раздела: **рейтинг синглов** строится только по релизам, оценки которых
подтвердили **все** участники (остальные показаны внизу с подсказкой «оценок пока нет»
или «ждём подтверждения всех оценок»).

- **Оценка** одна на релиз: ползунок 0–10 и число, затем подтверждение — как у трека.
  Неподтверждённый балл виден в средних на странице, но не попадает в рейтинг синглов.
  Подпись «подтверждён» и уведомление о подтверждении учитывают обоих участников:
  «сингл в рейтинге» появляется только когда оценки подтвердили все, а до того честно
  пишется «ждём оценку второго участника» или «ждём подтверждения второго участника».
- **Страница сингла** — компактная карточка релиза: обложка, год, артист, балл,
  блок своей оценки и строка привязки к альбому.
- **Привязка к альбомам** необязательна. При создании сингла или через «изменить»
  перечислите названия через запятую: `MUSIC, MUSIC — демо-издание`. Подсказки
  дополняют последнее название, повторы игнорируются, неизвестное или неоднозначное
  название не сохраняется. Названия с запятой заключайте в двойные кавычки
  (при выборе из подсказок это делается автоматически).
  «Отвязать» или пустое поле убирает все привязки; можно удалить лишь одно название.
  На странице каждого выбранного альбома виден сингл. Если альбомов несколько,
  только на странице сингла серая подчёркнутая кнопка **«показать еще...»**
  стоит сразу после первого альбома и раскрывает остальные ссылки в той же строке:
  через запятую, перед последним альбомом — «и». Первый альбом не повторяется.
  На карточках общего списка и при единственной привязке этой кнопки нет.
  У кнопок одинаковые отступы; раскрытие и сворачивание анимированы, кроме режима
  уменьшенного движения в настройках устройства.
  Снятие привязки не удаляет уже добавленные треки и их оценки (метка снимается отдельно).
- **Метка трека**: у каждого трека на странице альбома есть кнопка «отметить как
  сингл». Создаётся карточка сингла (название трека, год и обложка альбома), на треке
  появляется бейдж «сингл». Клик по бейджу открывает сингл сразу, клик по строке трека
  спрашивает «Перейти на страницу сингла?» (да / назад); клик по плашке модалку не
  открывает. Повторная кнопка снимает метку — карточка сингла и его оценки остаются.
  Подпись «Отмечен синглом в N альбомах» считает уникальные альбомы с такими метками
  и учитывает склонение: «в 1 альбоме», «в 11 альбомах», «в 21 альбоме». Без меток скрыта.
- **Сингл — это тоже трек**: когда сингл привязан к альбому, он появляется в конце
  списка треков этого альбома и получает бейдж «сингл». Если трек с таким названием
  уже есть, дубль не создаётся — существующий трек просто помечается. Если артист
  сингла отличается от артиста альбома, название записывается как «Название & Артист»
  — совместка со ссылкой на профиль артиста, как у обычных фитов (`ft.` / `feat.` / `&`).
  При зафиксированном количестве треков список не меняется, о чём сообщает уведомление.
- **Обложка**: пока своей нет — берётся у первого выбранного альбома (у самостоятельного сингла — плашка
  с буквой). Свою можно задать или заменить тем же окном, что и у альбома (файл или ссылка).
- **Удаление** — отдельная кнопка на странице сингла, с подтверждением и анимацией.
  Снятие метки и удаление альбома сингл не удаляют: при удалении альбома он остаётся
  с остальными привязками (или без привязок, если удалён последний альбом). Управлять синглами и метками могут оба участника.

Раздел требует обновления базы: `albums.kind`, `albums.parent_album_id`, `albums.parent_album_ids`,
`tracks.single_id`, таблица `single_ratings` с политиками и уникальность
«артист + название» с учётом типа релиза. В SQL Editor выполните `migrate.sql`
(существующая база) или `schema.sql` (новая). Пока миграция не выполнена, раздел
синглов на главной показывает напоминание, а альбомы работают как раньше.
Демо-сид: один самостоятельный сингл и три привязанных. MOJO JOJO размещён на MUSIC
и MUSIC — демо-издание, чтобы проверить несколько привязок.

Для новой возможности **повторно выполните `site/migrate.sql` в Supabase SQL Editor**.
Миграция сохраняет прежние одиночные привязки, проверяет ссылки и при удалении
альбома убирает только его из списка. Обновления используют существующий Realtime
таблицы `albums`.

## Два режима

| Режим | Когда | Данные |
|-------|-------|--------|
| **Демо** | `supabaseUrl` пуст или адрес `/?demo=1` | localStorage — только на этом устройстве |
| **Облако** | указаны ключи Supabase | общая база для двоих + живая синхронизация |

Превью без облачной базы: `cd site && python3 server.py --demo`, затем порт 8080.
Параметр `?demo=1` использует только localStorage и демо-учётные записи, не меняя `config.js`.

Демо-вход: `killmiplag@demo.local` / `demo` или `elevator@demo.local` / `demo`.

## Подключение Supabase

1. **Создайте проект** на https://supabase.com (бесплатно).
2. **Project Settings → API** — скопируйте **Project URL** и **anon key**.
3. Вставьте их в `config.js` (поля `supabaseUrl`, `supabaseAnonKey`).
4. Там же замените почты участников на настоящие:
   ```js
   allowedUsers: [
     { email: "ваша@почта.домен", username: "киллмиплаг", initials: "к", admin: false },
     { email: "почта@второго.домен", username: "Elevator", initials: "E", admin: true },
   ]
   ```
5. **SQL Editor → New query**:
   - новая база — вставьте `schema.sql` и нажмите Run;
   - база уже создавалась раньше — вставьте `migrate.sql` (можно повторять).
6. **(Рекомендуется)** Authentication → Sign In / Providers → Email →
   отключите «Confirm email», чтобы регистрация входила сразу.
7. Откройте сайт → «создать» → зарегистрируйте оба аккаунта
   (почта должна совпадать с `allowedUsers`).

## Как добавить обложку к существующему альбому

1. Войдите и откройте нужный альбом.
2. Под обложкой нажмите **«добавить обложку»** (если её нет) или
   **«изменить обложку»**.
3. Выберите изображение до **10 МБ** или вставьте прямую HTTP(S)-ссылку
   на изображение. Дождитесь предпросмотра.
4. Нажмите **«сохранить»**. До успешного сохранения старая обложка не меняется.
   **«отмена»** или **Escape** закрывают окно без изменений.

Окно и затемнение фона плавно появляются и исчезают. Если в системе включено
уменьшение движения (`prefers-reduced-motion`), анимации практически мгновенные,
а закрытие не задерживается.

Функция доступна обоим участникам, в том числе для альбомов с зафиксированными
треками и типом релиза. Меняется только обложка — не треки, оценки или другие
поля альбома. Карточки и профиль артиста используют обновлённую обложку;
другой участник получает обновление через настроенный Supabase Realtime.

- **Файл:** браузер уменьшает изображение до 900 px по длинной стороне
  (без увеличения маленьких изображений) и сохраняет JPEG. В облачном режиме
  файл попадает в существующий бакет `covers`, а его публичный URL — в
  `albums.cover_url`. Для каждой загрузки создаётся новое имя, чтобы не мешал кэш.
- **Ссылка:** сохраняется сам URL, изображение не копируется в Supabase.
  Лучше использовать HTTPS. Если внешний сайт удалит изображение или запретит
  его показ, обложка перестанет загружаться; загрузка файла надёжнее.
- **Демо:** изображение/ссылка хранится в localStorage этого браузера.
  При нехватке места показывается ошибка, а прежняя обложка остаётся на месте.

Для этой функции **миграция базы не нужна**: используются существующие
`albums.cover_url`, бакет `covers` и политики обновления/загрузки из текущей схемы.
Повторно запускать `schema.sql` или `migrate.sql` ради этой правки не требуется.
При ошибке загрузки проверьте наличие бакета `covers` и права текущего пользователя.
Старые файлы автоматически не удаляются: их URL могут использоваться в других местах.

## Проверки идут сами в GitHub Actions

**Локально ничего запускать не нужно.** Файл `.github/workflows/tests.yml` запускает
проверки в облаке GitHub на каждый push и на каждый pull request:

| Шаг | Что проверяет |
|-----|----------------|
| `npm ci` | зависимости ставятся по `package-lock.json` |
| `npm run typecheck` | `app.ts` компилируется без ошибок типов |
| `npm run build` | из `app.ts` собирается `app.js` |
| сверка `app.js` | собранный бандл совпадает с закоммиченным — не забыли пересобрать |
| `npx playwright install --with-deps chromium` | браузер для тестов (с кэшем) |
| `npx playwright test` | браузерные сценарии, desktop + mobile |

Результат виден в репозитории: вкладка **Actions** → выбранный запуск. Зелёная галочка —
всё хорошо, красный крестик — что-то сломалось: в логе видно, какой шаг и какой тест упал,
а в разделе **Artifacts** того же запуска лежит отчёт `playwright-report` со скриншотами
и трейсами упавших шагов (скачать и открыть `index.html`).

При падении на шаге сверки бандла нужно пересобрать `app.js` (`npm --prefix site run build`)
и закоммитить результат — иначе сайт отдаёт старый код.

Тесты проверяют настольный и мобильный размеры экрана. Проверяются создание
альбома без обложки, загрузка/замена файлом и ссылкой, отмена, неверные и слишком
большие файлы, медленные ответы, нехватка localStorage, ошибки Storage/БД,
защита от повторного сохранения, Realtime, анимации окна и уменьшение движения.
`tests/singles.spec.ts` проверяет переключатель разделов, страницу сингла и её оценку
с подтверждением, рейтинг только по подтверждённым баллам, пометку трека как сингла,
бейдж и модалку перехода, привязку к альбому, удаление сингла и экран добавления.
`tests/realtime.spec.ts` дополнительно проверяет два независимых сеанса участников,
фокус клавиатуры и слайдер, сохранение прокрутки и черновиков, задержанные чтения
и записи, подтверждения и удаления, ошибки и переподключение, резервную сверку,
скрытую вкладку, выход/повторный вход и обновление остальных экранов.
Облачные запросы и WebSocket
подменяются тестовыми ответами — **настоящая база Supabase не используется**.

Если когда-нибудь понадобится прогнать то же самое локально, команды такие:
```bash
cd site && npm ci && npm test
```
Это не обязательно: те же проверки выполняет GitHub Actions.

## GitHub, Arena и публикация на Cloudflare

У этого проекта два независимых слоя:

- **Cloudflare** раздаёт HTML, CSS и собранный `app.js` (сам сайт).
- **Supabase** хранит аккаунты, альбомы, треки, оценки и загруженные изображения.
  Подключение задано в `config.js`.

Подключение GitHub к Arena даёт агенту доступ к коду. Это **не означает**, что
каждая правка сразу появляется на рабочем сайте:

1. Агент меняет код в отдельной рабочей ветке, не затрагивая `main`.
   Изменения сохраняются в сессии Arena, но это не то же самое, что отправка в GitHub.
2. Вы проверяете изменения и превью. Тесты и демо-превью не должны менять рабочую базу.
   Обычный локальный запуск с текущим `config.js`, напротив, подключается к тому же
   Supabase, что и опубликованный сайт; для ручных экспериментов используйте демо-режим.
3. После согласования агент может сделать commit, push рабочей ветки и открыть
   **pull request** — предложение внести эти изменения в `main`.
4. После принятия pull request сайт обновится автоматически, **только если**
   Cloudflare связан с репозиторием и настроен деплой из `main`. Если сайт загружался
   вручную, потребуется отдельно опубликовать обновлённые статические файлы.

### Конфигурация Workers Builds

В **корне репозитория** находится `wrangler.jsonc`. Он указывает существующий
Worker **`albumratings`** и папку статических ресурсов **`./site`**. Поэтому
Wrangler знает, что публиковать, даже когда команда запускается из корня,
а не из `site/`. Без этой конфигурации `wrangler versions upload` завершался
ошибкой `Missing entry-point to Worker script or to assets directory`.

Серверный Worker-скрипт не нужен: сайт работает как Workers Static Assets,
а серверные данные обслуживает Supabase. **Не указывайте `site/app.js` как `main`**
в конфигурации Wrangler — это браузерный код, а не серверный обработчик.

Для этой структуры проекта настройки Cloudflare **Settings → Build**:

| Настройка | Значение |
|-----------|----------|
| Root directory | корень репозитория (`/`), **не** `site/` |
| Production branch | `main` |
| Build command | можно оставить пустой: собранный `site/app.js` уже хранится в Git |
| Deploy command (production) | `npx wrangler deploy` |
| Non-production branch deploy command | `npx wrangler versions upload` |

Команда `versions upload` создаёт версию для проверки ветки, не переключая на неё
рабочий сайт. После слияния PR в `main` production-команда `deploy` публикует
обновление. Текущую команду `npx wrangler versions upload` менять для исправления
этой ошибки не требуется: она автоматически прочитает новый `wrangler.jsonc`.
Новый Worker, база или токен для этого не нужны.

### Какие файлы публикуются

`site/.assetsignore` разрешает загрузку **только** `index.html`, `styles.css`,
`app.js`, `config.js` и каталога `covers/`. Исходники TypeScript, SQL, зависимости,
документация и тесты не публикуются как доступные по URL файлы.
При добавлении новых ресурсов для браузера обновляйте этот список разрешений.

`app.js` хранится в Git вместе с исходником `app.ts`: при изменении TypeScript
нужно обновлять оба. Для пересборки из корня репозитория:

```bash
npm --prefix site ci
npm --prefix site run build
```

При желании эти команды можно добавить в **Build command** Cloudflare:
`npm --prefix site ci && npm --prefix site run build`. Корневую папку при этом
оставьте `/`, чтобы Wrangler находил конфигурацию. Для Wrangler 4.129.0 нужен
Node.js 22+.

Проверка конфигурации и состава ресурсов **без загрузки в Cloudflare**, также
из корня репозитория:

```bash
npx wrangler@4.129.0 versions upload --dry-run
npx wrangler@4.129.0 deploy --dry-run
```

Документация Cloudflare: [Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/)
и [настройка Static Assets / `.assetsignore`](https://developers.cloudflare.com/workers/static-assets/binding/).

## Структура данных (облако)

- `profiles` — участники (id из auth.users, username, initials, avatar_url)
- `albums` — артист, название, год, обложка, tracks_locked, cohesion, album_type,
  `kind` (`album` | `single`), `parent_album_ids` (альбомы сингла)
  и `parent_album_id` (первая привязка, совместимость)
- `tracks` — треки альбома (title, position, locked, feat_artist, `single_id` — метка «сингл»)
- `ratings` — оценка участника на треке (score 0–10, confirmed)
- `single_ratings` — оценка участника на сингле целиком (album_id, profile_id, score 0–10, confirmed)
- `storage.buckets.covers` — обложки и аватары (публичное чтение)

Безопасность на RLS: читают/пишут только вошедшие; свои оценки, ник и аватар
меняет только их владелец; пароли хранит Supabase Auth.
